# FotoMag — правила работы с сайтом и приёмом заказов

Область этого файла — репозиторий `screamble123h/fotomag-print-hub`. Он описывает порядок работы и не выдаёт разрешений на другие проекты, оборудование, службы или внешние сообщения. Действующее поручение владельца определяет разрешённый объём действий.

## Перед началом

1. Прочитать [требования и архитектуру](docs/PROJECT.md), [эксплуатационный порядок](docs/OPERATIONS.md) и [протокол приёмки](docs/ACCEPTANCE.md). Последний содержит фактические результаты конкретного выпуска; намерения в плане не заменяют доказательства.
2. Проверить remote, ветку, HEAD и `git status`. Не терять пользовательские изменения; использовать отдельную ветку или worktree. Не применять `reset --hard`, `clean -fd`, force push или переписывание чужой истории для удобства выпуска.
3. Перед работой через Commander на `DESKTOP-P6L7HTI` прочитать `D:\FotoMag_PC_Stability\COMMANDER_SAFE_MODE.md` и действующие инструкции целевого проекта. Установить назначение папки по конфигурации запущенных компонентов, а не по её названию.
4. На Windows выполнять одну управляемую операцию за раз. После неопределённого тайм-аута сначала выяснить результат предыдущей операции. Выводить короткие сводки; не передавать через Commander большие файлы, base64, полные журналы и массивы клиентских данных.

## Границы изменений

- Публичные страницы, локальная форма, gateway, получатель файлов и Web-to-Print — разные компоненты. Изменение этого репозитория само по себе не обновляет работающий LAN-сайт или сервер.
- Сохранять главную, `souvenirs.html`, `mugs.html`, официальный логотип, утверждённые контакты и исходные изображения. Не заменять мастер-логотип выдуманным или переработанным знаком.
- Для каталога использовать `assets/mug-catalog.json` как источник карточки и заявки. Не переносить оптовую цену в розничную; неподтверждённая цена обозначается «Цену уточним».
- Не сокращать полную ссылку личного MAX. Не считать открытие приложения, копирование текста или запуск загрузки подтверждением заявки.
- Не добавлять APK, профили установки и внешние установочные страницы в Wi-Fi-сценарий. Не обещать подключение телефона только по нажатию веб-кнопки.
- Не публиковать токены, ключи, `.env`, приватные логи, клиентские фотографии, заказы, номера телефонов клиентов и служебные базы. Публичные контакты FotoMag сохранять в утверждённом виде.
- Не менять guards и чужие проектные инструкции для обхода ограничений. Не перезапускать автоматически службы, Docker, VPN, печать или Windows. `C:\ProgramData` с производственными службами и отдельный Web-to-Print не входят в обычную правку сайта.

## Выполнение и проверки

- Сначала исправлять потерю заявки, SKU, выбранного формата, ошибочную ссылку и ложный статус успеха. Затем — каталог, мобильное управление, Wi-Fi, скорость и оформление.
- Разделять работу параллельных исполнителей по файлам. Объединение, коммит, слияние PR, LAN-обновление и публикацию выполнять последовательно.
- Выполнять применимые команды из `docs/OPERATIONS.md`; не ослаблять существующий gate ради прохождения проверки. Добавлять проверки для конкретных регрессий.
- Проверять интерфейс при ширинах 360, 390, 430, 768 и 1366 px, с клавиатурой и увеличенным текстом. Соблюдать правила доступного механизма предпросмотра и браузера; отсутствие браузерной проверки указывать явно.
- Контрольные загрузки использовать только для нейтральных файлов в согласованном тестовом маршруте. Не отправлять сообщения реальным клиентам и не запускать физическую печать.
- Факт доставки на ПК подтверждать номером заявки, конечным путём, списком файлов, размерами и SHA-256. Локальный тест не подтверждает доступ из внешнего интернета.

## Выпуск и отчёт

- Порядок выпуска: отдельная ветка → Pull Request → обязательный `Validate site security` и остальные действующие проверки → разрешённое слияние → проверка GitHub Pages. Защиту `main` не обходить.
- Локальный LAN-сайт обновлять отдельной проверяемой процедурой с резервной копией и возвратом. Не публиковать незавершённую копию пофайловым копированием поверх рабочего каталога.
- Вести `docs/ACCEPTANCE.md`: для каждой задачи ID, цель, папка, ветка/коммит, критерий, наблюдаемый результат и следующий шаг. Различать «подготовлено», «реализовано», «проверено локально», «опубликовано», «подтверждено на рабочем ПК».
- Оркестратор считается работающим только после цепочки «задание → исполнение → проверенный результат». Очередь, реестр и планы без исполнителя этого не доказывают.
- Регулярный мониторинг считать настроенным только при наличии исполнителя, ID/названия, расписания `Europe/Samara`, журнала, способа остановки и успешного контрольного запуска. Не создавать дубли и не использовать обычные клиентские заказы как ежечасную проверку.
