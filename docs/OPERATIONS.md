# Разработка, выпуск и восстановление

Документ относится к FotoMag Print Hub. Исходная архитектура и требования находятся в [PROJECT.md](PROJECT.md), результаты текущего выпуска — в [ACCEPTANCE.md](ACCEPTANCE.md).

## 1. Подготовить рабочую копию

До правок проверить:

```bash
git remote -v
git branch --show-current
git rev-parse HEAD
git status --short --branch
```

Сверить repository/remote с `screamble123h/fotomag-print-hub`. Сохранить пользовательские изменения в старой копии и создать отдельную ветку или worktree от проверенной базы. Не сбрасывать старый checkout ради чистого статуса. Не создавать второй исполняющий процесс в той же рабочей папке.

На Windows сначала прочитать `D:\FotoMag_PC_Stability\COMMANDER_SAFE_MODE.md` и проектные инструкции. Затем ограниченной командой проверить устройство и инструменты, не выводя авторизационные файлы:

```powershell
$env:COMPUTERNAME
Get-Command git,node,codex
git --version
node --version
codex --version
codex login status
git -C 'D:\FotoMag_Site_Orders' status --short --branch
```

Вывод `login status` подтверждает состояние авторизации; содержимое `.codex/auth.json`, токены, окружение и приватные ключи не читать в отчёт. Рабочие версии и результат контрольного задания зафиксированы в PROJECT.md; при новом сеансе проверять актуальность.

## 2. Запуск и проверка клиентской части

Сайт использует статические HTML/CSS/JS, сборка приложения не требуется. Для обычной локальной среды разработчика можно обслуживать checkout только на loopback:

```bash
python -m http.server 8000 --bind 127.0.0.1
```

Этот сервер предназначен для просмотра клиентской части, не принимает заказы и не проверяет локальную производственную доставку. Не подставлять `http://localhost` в публичный API и не включать CORS/CSP для произвольных адресов.

В управляемой среде ChatGPT использовать предусмотренный механизм `sites-preview` и разрешённый браузерный инструмент. Не запускать второй preview-сервер, не устанавливать самостоятельный браузер и не обходить ограничения среды ради снимков экрана. Недоступность интерфейсной проверки записывать как ограничение.

### Проверки исходников и логики

Из корня репозитория:

```bash
python scripts/verify_public_site.py
python scripts/verify_souvenirs.py
python scripts/verify_mugs.py
python scripts/verify_performance_budget.py
node scripts/test_direct_upload.cjs
node --check assets/app-shell.js
node --check assets/direct-upload.js
node --check assets/mugs.js
git diff --check
```

`verify_mugs.py` вызывает `scripts/test_mug_order.cjs`: проверки используют функции из производственного `mugs.js`, проверяют текст заявки всех 139 товаров, SKU, ссылку, цену, цвет, количество и группировку. Отдельный запуск этого Node-теста возможен при работе только с каталогом.

`test_direct_upload.cjs` проверяет опасные переходы состояния загрузки в контролируемой тестовой среде. Он не заменяет HTTP-проверку работающего приёмщика и запись файлов на D:.

### Интерфейсные проверки

Действующий GitHub Actions workflow находится в `.github/workflows/site-security.yml`. Браузерные сценарии:

```bash
python scripts/test_personal_contacts.py
python scripts/test_souvenirs.py
python scripts/test_mugs.py
```

Для этих скриптов в обычном CI нужны предусмотренные workflow Python/Playwright и Chrome/Chromium. Версии и установку брать из workflow; не считать успешный статический анализ успешным браузерным прогоном.

Проверить основные состояния при 360, 390, 430, 768 и 1366 px, клавиатуру, видимый фокус, увеличенный текст и системную кнопку «Назад». Проверить главную, сервисы, личные каналы, ботов, каталоги, полный SKU-запрос, пустую категорию, крупное фото, переход к прямой форме, недоступный приёмщик и повтор/отмену загрузки. Сборку макета и работу выбора можно проверить без отправки сообщения.

Тесты не должны отправлять реальные сообщения клиентам, прикреплять клиентские фотографии, запускать физическую печать или создавать обычные заказы каждый час.

## 3. Публикация GitHub Pages

1. Проверить актуальный `main`, действующие ruleset, базу ветки и отсутствие неучтённых чужих изменений. При изменившейся базе аккуратно обновить рабочую ветку и повторить затронутые проверки.
2. Просмотреть diff, исключить секреты, приватные журналы, временные файлы, клиентские данные и неподтверждённые изображения/цены. Зафиксировать проверенный коммит.
3. Отправить рабочую ветку и открыть Pull Request. В описании указать проблему клиента, изменения поведения, проверки и ограничения. Владелец разрешил работу над сайтом, но правила доступа и обязательные проверки не обходятся.
4. Дождаться обязательного **Validate site security** и остальных требований репозитория на актуальном коммите PR. Не считать старый зелёный запуск проверкой нового HEAD.
5. Выполнить слияние штатным способом, если требования соблюдены. Прямой force push в `main`, отключение gate и ручная подмена результата не используются.
6. Проверить завершение GitHub Pages. Установить соответствие опубликованных ресурсов проверенному коммиту: сведения о Pages/Actions плюс содержимое или SHA-256 ключевых HTML/JS/CSS. HTTP 200 сам по себе не доказывает нужную версию.
7. Повторить основные клиентские маршруты по публичному URL. В `ACCEPTANCE.md` записать PR, merge SHA, результат CI/Pages, фактический URL, проверки и ограничения.

Публичная страница остаётся статической. Пустой `fotomag-upload-api` и ограничение `connect-src` не меняются на произвольный адрес ради прохождения проверки. Активация API требует установленного маршрута, корректных TLS/CORS/CSP, согласованной формы и подтверждения доступности.

## 4. Отдельный выпуск локальной формы

GitHub Pages и локальная копия не синхронизируются автоматически только потому, что исходники лежат в одном репозитории. Перед локальным выпуском подтвердить актуальные Caddy-конфигурации, Docker mounts и фактически обслуживаемый каталог.

На 28.11.2026 вход `dynv6:8443` использует `D:\FotoMag_MVP_20261125\site_v1\site`. Отдельный вход 443 и каталог `D:\FotoMag_LAN_SITE_20261126` проверяются самостоятельно.

Порядок локального обновления:

1. Установить, что нет другого исполнителя и активной клиентской передачи, которую затронет изменение. Сверить разрешённую область; не изменять попутно gateway, службы `C:\ProgramData`, Web-to-Print или guards.
2. Подготовить полный согласованный выпуск в отдельном каталоге с release ID, исходным коммитом и манифестом SHA-256. Переносить файлы ограниченными частями с проверкой результата, без больших ответов Commander.
3. Сделать проверяемую резервную копию действующего комплекта и конфигурации, участвующей в выпуске. Резервная копия не содержит новых изменений и имеет собственный манифест.
4. Проверить staging: основные ресурсы, точный адрес API, TLS/CORS/CSP, лимиты и интерфейс. Не публиковать часть JS с несовместимым HTML.
5. Использовать проверенный атомарный способ переключения комплекта, совместимый с существующим mount/сервером, без перезапуска производственных служб. Не считать обычное пофайловое копирование атомарным выпуском.
6. Если безопасное переключение в текущей архитектуре не обеспечено, оставить комплект подготовленным и зафиксировать конкретный блокирующий фактор. Не менять Docker mount, ACL или службы, чтобы скрыть это ограничение.
7. После переключения проверить фактически обслуживаемые файлы, контрольную загрузку, доставку, хеши и совместимость папок. В протоколе отделить «опубликовано на GitHub Pages» от «обновлено на LAN» и «подтверждена доставка».

Этот порядок задаёт критерии выпуска. Он не утверждает, что атомарный механизм уже установлен или что текущий LAN-комплект обновлён.

## 5. Контрольный заказ и внешняя доступность

Один согласованный контрольный маршрут использует только нейтральные файлы: JPG, PDF, кириллическое имя, несколько файлов и около 25 МиБ в пределах реального лимита. До начала дать тесту уникальный ID и сохранить исходные размеры/SHA-256.

Проверить серверную квитанцию и фактический путь на `D:\2026`. Подтвердить число файлов, имена, размеры, хеши, «Исходники» и «Обработанные JPEG». Не удалять и не перемещать реальные заказы для освобождения пути теста. Тестовые данные отмечаются как тестовые и не поступают на печать.

Повторить недоступность/обрыв и повтор так, чтобы проверить идемпотентность без неконтролируемых дублей. Зафиксировать поведение при закрытии формы. «Принято сервером» и «Доставлено на ПК» подтверждать соответствующими событиями, а не текстом, который интерфейс показал заранее.

Внешнюю доступность проверять из разрешённой внешней сети независимо от компьютера магазина. Результат должен различать ошибку DNS, TLS, порта, HTTP, приложения и блокировку самого диагностического инструмента. Запрет инструмента не обходить; если он мешает проверке, внешний результат остаётся неподтверждённым.

В публичной приёмке допустимы только нейтральные тестовые ID, пути и хеши без клиентской информации. Приватные технические журналы сохраняются на предусмотренном локальном месте и не добавляются в Git.

## 6. Восстановление

### Публичная версия

Зафиксировать дефект и последний работоспособный коммит. Подготовить **revert отдельным PR**, сохранив историю и защиту `main`. Учитывать изменения, пришедшие после плохого выпуска; не возвращать весь репозиторий старым архивом поверх чужой работы. Провести обязательный gate и после слияния сверить Pages с восстановленным коммитом.

Для merge-коммита выбор родителя при revert требует проверки графа; не выполнять шаблонную команду вслепую. Отмена публикации не отменяет уже принятые сервером заявки.

### Локальная форма

Остановить только дальнейшее развёртывание. Проверить состояние незавершённой передачи и сохранить диагностику. Вернуть предыдущий полный комплект через тот же проверенный способ переключения, используя сохранённую резервную копию и её хеши. Проверить отдаваемые ресурсы, доступность API и сохранность очереди/заказов.

Не очищать очередь, не удалять заказы, не откатывать базы без отдельной проверенной процедуры. Не перезапускать автоматически Windows, Docker, VPN, антивирус, принтеры и производственные службы. Если восстановление требует таких действий, сначала сохранить конкретный подготовленный план и обозначить границу разрешённого обслуживания.

## 7. Оркестратор и мониторинг

Работающий исполнитель для сайта в проверенном старом оркестраторе не подтверждён. Не записывать произвольное задание в незнакомую очередь и не объявлять его выполненным. Сначала установить формат, обработчик, журнал, получение результата и способ остановки. Если существует только планирование, продолжать разрешённую работу через отдельный контролируемый маршрут и честно указать статус.

Перед настройкой мониторинга проверить действующие задания и службы, чтобы не создать дубликат. Требуемый режим — примерно раз в час, Europe/Samara, без платных новых служб и без обычных тестовых клиентских заказов. Проверка кода запускается при изменениях.

Для приёмки мониторинга обязательны: реальное место исполнения, название/ID, расписание, часовой пояс, журнал, контрольный успешный запуск и команда/процедура остановки. Уведомления владельцу направляются только в явно согласованный для задачи канал; новый адрес не выбирается по предположению.

До записи этих фактов в ACCEPTANCE.md мониторинг считается планом, а не настроенной службой. Наличие ранее запущенного `FotoMag-Monitor` само по себе не подтверждает, что он проверяет новый публичный сайт и нужный приёмщик.
