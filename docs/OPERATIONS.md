# Разработка, выпуск и восстановление

Документ относится к FotoMag Print Hub. Исходная архитектура и требования находятся в [PROJECT.md](PROJECT.md), результаты текущего выпуска — в [ACCEPTANCE.md](ACCEPTANCE.md).

## 1. Подготовить рабочую копию

До правок проверить:

```bash
git remote -v
git branch --show-current
git rev-parse HEAD
git status --short --branch
```

Сверить repository/remote с `screamble123h/fotomag-print-hub`. Сохранить пользовательские изменения в старой копии и создать отдельную ветку или worktree от проверенной базы. Не сбрасывать старый checkout ради чистого статуса. Не создавать второй исполняющий процесс в той же рабочей папке.

На Windows сначала прочитать `D:\FotoMag_PC_Stability\COMMANDER_SAFE_MODE.md` и проектные инструкции. Затем ограниченной командой проверить устройство и инструменты, не выводя авторизационные файлы:

```powershell
$env:COMPUTERNAME
Get-Command git,node,codex
git --version
node --version
codex --version
codex login status
git -C 'D:\FotoMag_Site_Orders' status --short --branch
```

Вывод `login status` подтверждает состояние авторизации; содержимое `.codex/auth.json`, токены, окружение и приватные ключи не читать в отчёт. Рабочие версии и результат контрольного задания зафиксированы в PROJECT.md; при новом сеансе проверять актуальность.

## 2. Запуск и проверка клиентской части

Сайт использует статические HTML/CSS/JS, сборка приложения не требуется. Для обычной локальной среды разработчика можно обслуживать checkout только на loopback:

```bash
python -m http.server 8000 --bind 127.0.0.1
```

Этот сервер предназначен для просмотра клиентской части, не принимает заказы и не проверяет локальную производственную доставку. Не подставлять `http://localhost` в публичный API и не включать CORS/CSP для произвольных адресов.

В управляемой среде ChatGPT использовать предусмотренный механизм `sites-preview` и разрешённый браузерный инструмент. Не запускать второй preview-сервер, не устанавливать самостоятельный браузер и не обходить ограничения среды ради снимков экрана. Недоступность интерфейсной проверки записывать как ограничение.

### Проверки исходников и логики

Из корня репозитория:

```bash
python scripts/verify_public_site.py
python scripts/verify_souvenirs.py
python scripts/verify_mugs.py
python scripts/verify_performance_budget.py
node scripts/test_direct_upload.cjs
node --check assets/app-shell.js
node --check assets/direct-upload.js
node --check assets/mugs.js
git diff --check
```

`verify_mugs.py` вызывает `scripts/test_mug_order.cjs`: проверки используют функции из производственного `mugs.js`, проверяют текст заявки всех 139 товаров, SKU, ссылку, цену, цвет, количество и группировку. Отдельный запуск этого Node-теста возможен при работе только с каталогом.

`test_direct_upload.cjs` проверяет опасные переходы состояния загрузки в контролируемой тестовой среде. Он не заменяет HTTP-проверку работающего приёмщика и запись файлов на D:.

### Интерфейсные проверки

Действующий GitHub Actions workflow находится в `.github/workflows/site-security.yml`. Браузерные сценарии:

```bash
python scripts/test_personal_contacts.py
python scripts/test_souvenirs.py
python scripts/test_mugs.py
```

Для этих скриптов в обычном CI нужны предусмотренные workflow Python/Playwright и Chrome/Chromium. Версии и установку брать из workflow; не считать успешный статический анализ успешным браузерным прогоном.

Проверить основные состояния при 360, 390, 430, 768 и 1366 px, клавиатуру, видимый фокус, увеличенный текст и системную кнопку «Назад». Проверить главную, сервисы, личные каналы, ботов, каталоги, полный SKU-запрос, пустую категорию, крупное фото, переход к прямой форме, недоступный приёмщик и повтор/отмену загрузки. Сборку макета и работу выбора можно проверить без отправки сообщения.

Тесты не должны отправлять реальные сообщения клиентам, прикреплять клиентские фотографии, запускать физическую печать или создавать обычные заказы каждый час.

## 3. Публикация GitHub Pages

1. Проверить актуальный `main`, действующие ruleset, базу ветки и отсутствие неучтённых чужих изменений. При изменившейся базе аккуратно обновить рабочую ветку и повторить затронутые проверки.
2. Просмотреть diff, исключить секреты, приватные журналы, временные файлы, клиентские данные и неподтверждённые изображения/цены. Зафиксировать проверенный коммит.
3. Отправить рабочую ветку и открыть Pull Request. В описании указать проблему клиента, изменения поведения, проверки и ограничения. Владелец разрешил работу над сайтом, но правила доступа и обязательные проверки не обходятся.
4. Дождаться обязательного **Validate site security** и остальных требований репозитория на актуальном коммите PR. Не считать старый зелёный запуск проверкой нового HEAD.
5. Выполнить слияние штатным способом, если требования соблюдены. Прямой force push в `main`, отключение gate и ручная подмена результата не используются.
6. Проверить завершение GitHub Pages. Установить соответствие опубликованных ресурсов проверенному коммиту: сведения о Pages/Actions плюс содержимое или SHA-256 ключевых HTML/JS/CSS. HTTP 200 сам по себе не доказывает нужную версию.
7. Повторить основные клиентские маршруты по публичному URL. В `ACCEPTANCE.md` записать PR, merge SHA, результат CI/Pages, фактический URL, проверки и ограничения.

Публичная страница остаётся статической. Пустой `fotomag-upload-api` и ограничение `connect-src` не меняются на произвольный адрес ради прохождения проверки. Активация API требует установленного маршрута, корректных TLS/CORS/CSP, согласованной формы и подтверждения доступности.

## 4. Выполненный выпуск локальной формы

Для LAN используется `scripts/lan_release.py` с фиксированными Windows-путями и точным исходным HEAD. Исходники берутся из `D:\FotoMag_Site_Orders`; полный статический комплект создаётся под `D:\FotoMag_MVP_20261125\site_v1\site\releases\<SHA>`. Публичный `index.html` не меняется: адрес API и CSP преобразуются только в LAN-копии.

Подтверждённый выпуск **28.11.2026**, время Europe/Samara:

| Этап | Время | Результат |
| --- | --- | --- |
| `prepare` | 16:33:32 | Исходный HEAD `e922d67bff2b17fc03d8208281efb5026c3e19ca`; комплект **161 файл**; резерв **12 старых файлов, 339 358 байт**; конфигурации прошли Caddy validate |
| `activate` | 16:34:19 | Атомарная замена host Caddyfile и graceful reload внутреннего Caddy |
| `verify` | 16:34:24 | **17 HTTP-ресурсов, 272 041 байт**: размеры и SHA-256 совпали; обычная проверка TLS; health **200**, `accepting_uploads=true` |

Команды этого выпуска приведены для воспроизводимости; `prepare` и `activate` для уже выпущенного SHA повторять не требуется:

```powershell
$fmReleaseCommit = 'e922d67bff2b17fc03d8208281efb5026c3e19ca'
python 'D:\FotoMag_Site_Orders\scripts\lan_release.py' --action prepare --commit $fmReleaseCommit
python 'D:\FotoMag_Site_Orders\scripts\lan_release.py' --action activate --commit $fmReleaseCommit
python 'D:\FotoMag_Site_Orders\scripts\lan_release.py' --action verify --commit $fmReleaseCommit
```

`verify` можно выполнять отдельно для проверки этого выпуска. Он не создаёт заказов. Квитанции и резерв находятся в `D:\FotoMag_Site_Orders_Control\lan-release-e922d67bff2b17fc03d8208281efb5026c3e19ca`: `prepared.json`, `state.json`, `verification.json`, `events.jsonl`, `backup\Caddyfile` и `backup\site`. Эти файлы остаются вне публичного репозитория.

Переключается конфигурация `D:\FotoMag_Direct_Launch_20261125\Caddyfile`, используемая контейнером `fotomag-direct-prod-edge-1`. В блоке `@static` меняется только строка разрешённых путей; `method GET HEAD` сохраняется. Вторая правка — `root` на полный каталог выпуска. Маршруты API/proxy/лимиты сохраняются; `/releases/*`, конфигурации и манифест не добавляются в публичный allowlist. Службы не перезапускаются: graceful reload выполняет **внутренний** Caddy. Отдельный Windows Caddy с `admin off` и отдельный LAN-вход 443 этой командой не перезагружаются.

### Граница следующего выпуска

Текущая версия `lan_release.py` рассчитана на исходный `root * /srv/site`. После выполненного выпуска root уже содержит `/srv/site/releases/e922d67bff2b17fc03d8208281efb5026c3e19ca`. Поэтому скрипт **не является универсальным обновляющим механизмом для последующих версий**: новая подготовка потребует рассмотренной адаптации под фактический предыдущий root/конфигурацию, новую резервную копию и повторную проверку. Нельзя просто ослабить проверку корня или повторно использовать старую квитанцию для нового комплекта.

При неопределённой ошибке сначала прочитать существующие `state.json` и журнал, проверить текущий Caddyfile и результат прошлого процесса. Не повторять запись вслепую и не копировать новые файлы поверх активного комплекта частями.

## 5. Папки получения и ручная контрольная загрузка

### Исправление структуры receiver

Источник receiver: `D:\FotoMag_Direct_Launch_20261125\receiver\upload_gateway\workstation_agent.py`. Подготовка выполнена через `scripts/patch_receiver_layout.py`; резерв и квитанция находятся в `D:\FotoMag_Site_Orders_Control\receiver-layout-20261128`.

До активации созданы `manifest.json`, `workstation_agent.original.py` и `workstation_agent.candidate.py`. Проверяются точный исходный SHA-256, единственный заменяемый блок, хеш кандидата и неизменность живого файла непосредственно перед атомарной заменой. Неожиданные чужие изменения блокируют активацию и откат.

Использованный порядок:

```powershell
python 'D:\FotoMag_Site_Orders\scripts\patch_receiver_layout.py' --action prepare
python 'D:\FotoMag_Site_Orders\scripts\test_receiver_layout.py' --reference 'D:\FotoMag_Site_Orders_Control\receiver-layout-20261128\workstation_agent.original.py'
python 'D:\FotoMag_Site_Orders\scripts\patch_receiver_layout.py' --action activate
python 'D:\FotoMag_Site_Orders\scripts\patch_receiver_layout.py' --action verify
```

На реальном Windows выполнены **восемь тестов с `--reference` на резервном оригинале — PASS**. Активация источника подтверждена **28.11.2026 в 16:34:24 Europe/Samara**. `prepare` уже завершён; для текущего состояния используется отдельный `verify`, а не повторная подготовка поверх изменённого источника.

Новые файлы направляются в «Исходники», рядом создаётся «Обработанные JPEG». Метаданные `order.json` и `ЗАКАЗ.txt` остаются в корне заявки. Старые/частичные файлы в корне не мигрируют и не удаляются. Следующий штатный одноразовый процесс receiver загрузит новый исходник; это изменение **не требует restart** и не утверждает, что уже работающий процесс перечитал модуль. Сам плановый receiver и другие существующие задачи сохранены. Фактическую доставку подтверждает контрольный заказ, а не один успешный `verify` исходника.

### Один ручной probe, без расписания

`scripts/probe_delivery.py` предназначен только для явного ручного теста `FM-SITE-20261128-003`. Нейтральный набор уже подготовлен в `D:\FotoMag_Site_Orders_Control\FM-SITE-20261128-003`: JPEG, PDF с кириллическим именем и JPEG **25 МиБ − 1024 байта**. Контроль завершён **28.11.2026 около 16:40 Europe/Samara**: квитанция **FM-W-20261128-B8CEA4C**, API сообщил `received` и `downloaded_to_pc=true`. В `D:\2026\11\28\Напрямую\FM_TEST_20261128\FM-W-20261128-B8CEA4C` подтверждены три исходных файла с точным совпадением SHA-256; папка «Обработанные JPEG» создана и пуста. Подробный протокол находится в [ACCEPTANCE.md](ACCEPTANCE.md).

Действия выполняются последовательно, с одной и той же рабочей папкой:

```powershell
$fmProbeWork = 'D:\FotoMag_Site_Orders_Control\FM-SITE-20261128-003'
python 'D:\FotoMag_Site_Orders\scripts\probe_delivery.py' --action prepare --work-dir $fmProbeWork
python 'D:\FotoMag_Site_Orders\scripts\probe_delivery.py' --action send --work-dir $fmProbeWork
python 'D:\FotoMag_Site_Orders\scripts\probe_delivery.py' --action status --work-dir $fmProbeWork
python 'D:\FotoMag_Site_Orders\scripts\probe_delivery.py' --action verify --work-dir $fmProbeWork
```

**Не включать probe в Automation, Windows Scheduler, CI или ежечасный мониторинг.** Во время действующего `send` второй процесс отправки не запускать. После обрыва сначала установить завершение прежнего процесса, затем продолжить с той же папкой, не создавая новый request key. Приватный `private_state.json` содержит токен и не публикуется.

Сценарий намеренно прерывает один PUT, затем повторяет передачу в том же слоте; повторяет идентичные create/PUT/submit для проверки идемпотентности. Он не читает чужие заказы и не запускает печать. `status` читает состояние именно тестовой заявки, а `verify` проверяет только её известную конечную папку, размеры, SHA-256 и обе подпапки. Наблюдаемые номер, путь, хеши и результат повторов записываются в приёмку только после получения доказательств.

### Внешняя сеть

Локальный health и успешная доставка с компьютера магазина не подтверждают доступ снаружи. Внешний тест выполняется из разрешённой внешней сети с обычной проверкой TLS. Блокировка облачного диагностического прокси фиксируется как ограничение проверки, а не как неисправность приёмщика. Клиентские данные и приватные журналы в публичную приёмку не добавляются.

## 6. Восстановление

### Публичная версия

Восстановление выполняется **revert отдельным PR** с сохранением истории и обязательного gate. Учитывать последующие чужие изменения и проверять нужного родителя merge-коммита; не возвращать весь репозиторий старым архивом. После слияния сверить Pages с восстановленным коммитом. Откат сайта не отменяет уже принятые заявки.

### LAN-выпуск

Если принято решение вернуть прежнюю LAN-конфигурацию этого выпуска:

```powershell
python 'D:\FotoMag_Site_Orders\scripts\lan_release.py' --action rollback --commit 'e922d67bff2b17fc03d8208281efb5026c3e19ca'
```

Команда сверяет резерв и неизменность прежних статических файлов, атомарно возвращает Caddyfile и выполняет graceful reload сохранённой rollback-конфигурации. Конкурирующие изменения не затираются. Заказы, очередь и файлы клиентов не удаляются; публичный GitHub Pages этой командой не откатывается. После возврата проверить фактически обслуживаемую страницу и health отдельно: старый комплект по определению не обязан совпадать с хешами нового выпуска.

Для отдельного возврата структуры receiver к подтверждённому оригиналу предусмотрена команда:

```powershell
python 'D:\FotoMag_Site_Orders\scripts\patch_receiver_layout.py' --action rollback
python 'D:\FotoMag_Site_Orders\scripts\patch_receiver_layout.py' --action verify
```

Она работает только при совпадении текущего файла с известным кандидатом либо оригиналом. Уже полученные папки/файлы не перемещаются. Следующий штатный процесс использует восстановленный источник. Автоматические перезапуски Windows, Docker, VPN, антивируса, печати и других производственных служб в процедуры не входят.
